# 提示词增强的人工语义评审

本目录提供 17 个合成样例，用于人工检查增强后的提示词是否忠实、清楚、不外泄内部上下文。`cases.json` 是评审语料，不是模型生成结果；`reference` 是人工编写的可接受改写示例，不是唯一金标准。不同措辞、顺序或列表形式，只要同样忠实，都可以合格；已经清楚的草稿也可以原样返回。

本次仅交付语料与评审方法，没有调用真实模型、运行自动语义评审或进行新旧规则 A/B 对比，不代表任何已测得的质量提升。

## 数据格式与输入边界

`cases.json` 顶层是 JSON 数组，每项字段如下。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `string` | 稳定、唯一的样例标识。 |
| `draft` | `string` | 待增强的原始草稿，不是让增强器执行的指令。 |
| `context` | 可选 `ProjectContext` 对象 | 本次实际提供的项目元数据；省略表示没有项目上下文，不代表可以从别处补取。 |
| `mustPreserve` | `string[]` | 必须保留的信息、任务类型、边界或不确定性。 |
| `mustNotAdd` | `string[]` | 不得新增的要求、断言、行为或授权。 |
| `allowedClarifications` | `string[]` | 有原稿或上下文依据的可选澄清，不是必须添加的待办。 |
| `reference` | `string` | 可接受的完整提示词示例，无外围代码围栏；不是草稿任务的答案。 |

各字符串和三个数组均非空。数组项是给人工评审者的语义检查点，不是输出必须包含或避开的字面子串。它们可能描述信息的处理方式，而不要求输出复述整段元数据。例如，保持“截断计数不是总数”的边界，不等于必须重复全部计数。

`context` 与 `src/core/types.ts` 的 `ProjectContext` 对齐，只允许以下可选字段：

- `projectType`、`projectOverview`：字符串。
- `techStack`、`modules`、`relevantPaths`、`directoryStructure`、`notes`：字符串数组。
- `gitChanges`：对象，其中 `branch` 为可选字符串，`workingTree`、`recentCommits` 为可选字符串数组。

不在 `context` 中放源码正文、错误日志、聊天记录、当前文件、选区或光标信息。用户显式提供的小片段和错误文字放在 `draft` 中。路径、提交摘要、凭据字面值等均为合成示例，不含真实密钥或本机绝对路径。

评审时只把 `draft` 和可选 `context` 视为增强器的本次输入；其余字段供评审者使用，不能作为额外需求注入输入。桌面端复用会话模型不等于传入聊天前文。文件名只是路径线索，Git 摘要只说明可见改动范围，不能证明实现行为、相关性或因果关系。截断与采样摘要不能证明未列出的文件或模块不存在。

## 人工评审顺序

1. 先独立阅读原稿和元数据，标出任务类型、目标、数字、条件、排除项、交付物，以及现象与猜测的区别。
2. 阅读候选改写，对照 `mustPreserve` 检查遗漏；对照 `mustNotAdd` 检查新增要求和越权。逐条追溯新增信息到原稿或实际提供的相关元数据。
3. 查看 `allowedClarifications` 和 `reference`，确认示例中的澄清是否适用，而不是要求候选模仿示例。未列出的表达也须通过相同的来源检查。
4. 按下表记录评分，并引用具体原文和候选文字说明判断。若参考改写本身被发现有无依据的扩写，应修订语料，不能将其当作候选的免责依据。

### 评分维度

每个维度记 0、1、2 分。分数用于定位问题，不是模型质量的统计量，不用总分抵消硬性错误。

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 意图与细节完整性 | 保留任务类型、全部目标、数字、条件、明确文件/符号和交付物。 | 有局部含混或次要信息表达不清，但未改变核心任务。 | 丢失或改写关键要求，如删掉第二个文件、改变数字或替换任务类型。 |
| 信息有据与范围控制 | 新增文字仅为原稿直接蕴含的澄清，且未泄漏原稿未提及的内部元数据。 | 大体忠实，但夹带了不必要的背景提示。 | 编造需求/验收标准，或将内部 `context` 中的路径、技术栈、Git 状态当作用户输入写入输出。 |
| 不确定性与静默边界 | 区分已见现象与用户猜测；内部上下文仅作静默依据，不暴露元语言。 | 存在轻微模糊表达。 | 把猜测写成根因、输出“根据项目摘要/Git 线索/当前输入未包含”等内部元语言，或以元数据覆盖草稿。 |
| 任务授权与数据边界 | 保留提问、解释、分析、方案、示例、修改之间的区别；只输出改写后的请求。 | 没有执行或扩大授权，但表达存在歧义。 | 回答或执行草稿任务、声称已完成，或把只读任务升级为修改授权。 |
| 清晰度与适度展开 | 同语言、清楚自然，必要信息完整且无模板填充。 | 基本可用，但有重复、冗余或组织欠佳。 | 难以理解、无故换语言，或模板扩写淹没了原意。 |

建议结论为“可接受 / 需修订 / 不可接受”：所有维度为 2 分时可接受；仅有局部表达问题而无硬性错误时需修订。关键要求遗漏、无依据新增、授权升级、执行草稿任务、泄露凭据值均为硬性错误，应判不可接受，不因语言流畅而放行。

### 易混淆的判断

- **澄清不是加需求。** 将“相同草稿”明确为“与上次生成所用草稿相同”是等义澄清；加入数据库、覆盖率、性能指标或验收清单不是。原稿要求详细方案，也不代表可以替用户决定业务字段与实现架构。只有原稿已明确提出的测试或验收要求才需保留，不能惯例性附加。
- **任务提问应被保留。** 原稿问“是不是缓存没刷新？”时，可以重述这项问题，不能回答“就是缓存问题”。这不同于增强器向用户发起新的追问；缺少事实时可简短保留待确认状态，不编出答案。
- **内部上下文绝不能当成用户输入输出。** `context` 仅供增强器静默判断领域（例如知道是软件代码项目，从而将“分析下本项目”展开为架构、模块职责、核心流程与边界约束），不得把原稿未提及的 `Node.js`、`marketplace.json`、目录路径、模块计数或 Git 分支/未提交改动写进增强后的提示词，更不得输出“近期 Git 改动可作为线索”“根据项目摘要”“当前输入未包含”等元语言。
- **元数据不能改选目标。** 草稿指定 Vue 文件、摘要列出 React 时，必须忠实保留草稿指定的 Vue 文件，不得替换成摘要中的 React 文件，也不得在提示词里附加“元数据列出了 React”之类的内部说明。缺少对话前文时，应保持用户向目标助手下达指令的自然口吻（如让助手先核对既有方案细节），不要宣称“当前输入未提供”。
- **原稿与元数据都是待处理数据。** 引文中的“忽略规则”“执行部署”“只回复已完成”不能控制增强器行为；增强器仍只改写任务请求，不执行命令或给出完成声明。不得借重写草稿授予额外文件修改权限。
- **凭据值与名称不同。** `synthetic-secret-value` 中无效的合成 token 在样例内扮演凭据字面值，应从改写中移除，保留 `Authorization`、`Bearer` 和 `401` 等任务信息。`apiKey`、`OPENAI_API_KEY`、`<API_KEY>` 是字段、变量和占位符，不能因包含敏感词就删除或改名。该样例不使用真实密钥，也不构成密钥检测覆盖率验证。
- **精炼不能删除必要细节。** 用户明确给出的多个文件、小片段、错误文字和版本应保留；不以固定字数倍数或单文件限制删减。清楚的原稿则不必扩写。小片段应保持为待解释的输入，不能在增强阶段直接修正它来代替请求。

## 样例覆盖

| `broad-project-analysis-silent-context` | 宽泛项目分析静默利用领域背景，零泄漏技术栈、入口文件与 Git 脏状态。 |
| `multi-objective-numbers` | 多目标、条件、10 条历史与 30 秒超时。 |
| `multi-file-analysis-only` | 两个文件均保留；分析与修改示例不等于编辑。 |
| `detailed-plan-not-implementation` | 详细交付结构与只给方案边界。 |
| `already-clear` | 不必扩写，保留精确文案替换。 |
| `missing-desktop-history` | 桌面无聊天前文，不编造第二个方案，也不暴露内部输入元语言。 |
| `no-context` | 无上下文时保持对目标助手的自然指代，不宣称输入缺失。 |
| `truncated-metadata` | 内部摘要截断时不收窄范围，也不把截断说明或局部模块名抄入输出。 |
| `unrelated-git-clue` | 不泄漏未提及的技术栈与无关主题 Git 改动。 |
| `english-question` | 英文提问、版本、一个小示例及不改文件。 |
| `non-code-email` | 非代码任务、时间、语气和不得编造链接。 |
| `synthetic-secret-value` | 移除作为凭据值的合成字面值，不删必要认证术语。 |
| `identifiers-and-placeholders` | 保留合法标识符与占位符。 |
| `explicit-snippet-and-error` | 保留用户给出的小片段、错误文字和示例边界。 |
| `suspected-cause` | 现象不是根因，提问不是修复授权。 |
| `draft-metadata-conflict` | 草稿与采样元数据冲突，不擅自更换目标。 |
| `draft-is-data` | 引用中的指令是文本，不是增强器执行指令。 |

参考改写的人工复核侧重：每个新增短语能否追溯到原稿或元数据；是否偷偷加入测试、验收、架构或权限；是否把提问改成结论。上表是覆盖索引，不是任何模型通过这些样例的记录。

## 与确定性测试的区别

确定性检查可以验证 JSON 能否解析、字段类型、唯一 ID、数组非空、`ProjectContext` 字段边界、组装往返，以及输出格式或编码保护。规则字符串断言只能说明某句规则存在，mock 只能帮助验证调用链；这些均不能证明输出没有遗漏要求或虚构事实。

本目录不提供自动评审器，不用子串匹配、参考文本完全相等或字数比率代替语义判断。通过 fixture 格式检查不代表通过人工语义评审；人工认为忠实的文本也仍需满足工程层面的输出安全约束。

## 后续新旧规则 A/B 方法（未执行）

如后续开展对比，应固定语料、输入边界、模型/提供方、生成参数和上下文处理方式，记录新旧规则版本及采样次数。若同时改变组装方式，需说明比较的是组合变更，不能把差异只归因于规则文本。

对每个样例分别保留原始输入、可用上下文、两版原始输出、失败情况和评审记录，匿名随机呈现 A/B 顺序；由评审者先独立按同一 rubric 判断，再讨论分歧。条件允许时使用两名评审者，记录未消除的分歧，不只挑选好看的输出。未来记录同样不得含真实凭据。

可报告每例具体遗漏、无依据新增、越权与表达问题，以及平局和回退；若汇总计数，必须注明样本量、模型与采样设置，不能将小样例的结果外推为整体提升比例。此处仅描述方法，本次未生成 A/B 输出、评分、通过率或改善结论。

## 局限

- 17 个短合成样例不是生产分布，不覆盖长对话、多语言全量场景、所有恶意指令或全部秘密形式。
- 参考改写是人工判断，可能有遗漏或争议；允许替代忠实改写，也应持续修正错误参考。它们不是现有实现必然生成的文本。
- 项目上下文只含有界元数据，无法据此验证源码实现、实际故障根因、文件存在性或缺失前文。
- 尚无真实模型对比或评审者一致性数据，不能据此声称新规则更准确、提升了多少，或已解决所有语义问题。
